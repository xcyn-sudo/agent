## 1. 业务摘要

### 1.1 产品定位

**一句话**：让每个员工都能像问资深同事一样，秒级获取企业知识。

**详细定位**：企业知识中枢是一个面向中型及以上企业的内部智能知识平台。它打通散落在各个业务系统（ERP、CRM、OA、文件服务器）的孤岛数据，让员工用自然语言提问，获得精准、可溯源、受权限管控的答案。

### 1.2 核心业务价值

| 价值维度 | 现状 | 目标 |
|---------|------|------|
| 知识查找效率 | 新员工平均花 **23 分钟** 找一份制度文件 | **10 秒** 内得到答案 |
| 跨部门信息获取 | 需要发邮件/钉钉问人，**平均等待 4 小时** | 即时自助获取 |
| 重复咨询 | 70% 的员工问题是重复的（"报销流程是什么"） | AI 承载 80% 的重复咨询 |
| 知识沉淀 | 老员工离职带走隐性知识，**无留存** | 文档化 + 可检索的知识库 |
| 数据合规 | 敏感数据（薪资、合同）无访问控制 | 按部门+职级+密级的细粒度权限 |

### 1.3 目标用户

| 用户 | 核心诉求 | 使用频率 |
|------|---------|---------|
| **一线员工** | 快速查制度、流程、规范，不想翻文件夹 | 每天 3-5 次 |
| **中层管理者** | 查本部门数据报表，上传更新部门制度 | 每天 1-2 次 |
| **高层管理者** | 跨部门全局视角，数据驱动决策 | 每周 2-3 次 |
| **IT 管理员** | 管理数据源、用户权限、系统配置 | 初期频繁，后期维护 |

## 2. 业务痛点全景

### 痛点 1：知识散落各处，查找成本极高

```
┌─────────────────────────────────────────────────────────────┐
│                    员工的一天                                  │
│                                                             │
│  想查"绩效考核周期"                                          │
│    ↓                                                        │
│  打开企业网盘 → 搜索"绩效" → 128 个结果                       │
│    ↓                                                        │
│  翻到第 3 页找到《2024年绩效考核制度 v3.2 final 终版(2).docx》│
│    ↓                                                        │
│  打开 → 68 页 → 翻到第 24 页 → 找到答案                       │
│                                                             │
│  用时：23 分钟。答案："季度考核，每年 4 次"                      │
└─────────────────────────────────────────────────────────────┘
```

**影响量化（以 200 人规模企业为例）**：

| 指标 | 数值 | 计算方式 |
|------|------|---------|
| 平均查找一份制度文件耗时 | 23 分钟 | 实测：打开网盘→搜索→翻页→打开→定位 |
| 员工日均信息查找次数 | 3.5 次 | 含制度/流程/规范/项目信息 |
| 人均日耗时 | 80 分钟 | 3.5 次 × 23 分钟 |
| 人均年耗时 | 280 小时 | 80 分钟 × 250 个工作日 ÷ 60 |
| 200 人公司年工时损失 | **56,000 小时** | 相当于 28 个全职员工全年工作量 |
| 人工成本损失（按时薪 80 元计） | **448 万元/年** | 56,000 × 80 |
| 因查不到而"放弃查找"占比 | 31% | 员工干脆不问/不查，凭感觉做事 |
| 因信息错误导致的返工 | 年均 12 次/人 | 用了过期制度、错误流程 |

### 痛点 2：业务系统数据孤岛，查一个信息要切多个系统

```
员工想了解"自己部门的预算执行情况 + 相关审批流程"

需要：
  1. 登录财务系统 → 查预算报表
  2. 登录 OA 系统 → 查审批流程文档
  3. 打开邮件 → 找 CFO 上周发的预算调整通知
  4. 问直属领导 → "这个数字什么意思"

信息分布在 4 个不同的地方，没有一个统一的入口
```

### 痛点 3：经验在脑子里，不在系统里

```
场景：公司唯一懂 Oracle 数据库优化的 DBA 离职了。

后果：
  - 他写的《数据库运维手册》是 3 年前的版本，没人更新
  - 他处理过的 200+ 个故障案例，口头传授给了徒弟一部分
  - 徒弟也离职了
  - 新来的 DBA 从零开始摸索
  - 一次数据库故障处理时间从 30 分钟变成 4 小时
```

### 痛点 4：敏感数据缺乏防护，谁都能看

```
现状：
  - 公司薪资文件放在共享盘"HR 部"文件夹下
  - 文件夹权限：HR 部门所有人可读写
  - 但实际上 IT 管理员也能访问（因为他是 admin）
  - 研发部实习生通过"搜索"功能也能搜到薪资文件

等保合规要求：
  - 不同密级数据需要不同的访问控制
  - 需要审计日志：谁、在什么时间、访问了什么数据
```

### 痛点 5：重复问题反复回答，管理者很累

```
HR 总监每周收到的问题：
  - "年假怎么算？" — 第 47 次
  - "异地调动的补贴政策是什么？" — 第 23 次
  - "生育保险报销需要什么材料？" — 第 15 次

为什么不去看制度文件？
  → "文件太长了找不到"
  → "看了没看懂，不如直接问人"
```

## 3. 解决方案概述

### 3.1 核心思路

```
痛点                          解决方案                          最终效果
────                          ────────                          ────────
知识散落各处，查找成本高  →  统一知识中枢，自然语言搜索     →  10秒找到答案
业务系统数据孤岛         →  多源数据接入，统一查询入口       →  一个框查所有系统
经验在脑子里，不在系统里  →  文档上传+自动切片+RAG检索       →  离职文档不丢，隐性知识显性化
敏感数据无防护           →  ABAC 属性级权限控制              →  什么人看什么数据，全程审计
重复问题反复回答         →  智能问答自动回答80%重复问题      →  管理者时间释放
```

## 5. 业务功能详解

### 5.1 智能问答（核心功能）

**解决的业务痛点**：痛点 1（查找成本高）、痛点 5（重复问题）

#### 5.1.1 自然语言搜索

**功能描述**：员工用日常语言提问，系统从知识库中检索相关信息并生成精准答案。

**和传统搜索的区别**：

| 对比维度 | 传统企业搜索（关键词） | 企业知识中枢（自然语言） |
|---------|---------------------|------------------------|
| 输入方式 | "绩效考核 制度 2024" | "研发部2024年的绩效考核周期是多久？" |
| 返回结果 | 128 个文件列表 | 一个精准答案 + 引用来源 |
| 理解能力 | 字面匹配 | 理解"薪酬=工资=薪水=报酬" |
| 溯源能力 | 点开文件自己找 | 直接告诉你是哪份文档、哪一章节 |
| 学习成本 | 需要知道正确的"关键词" | 用日常语言即可 |

**典型使用场景**：

| 场景 | 问题示例 | 理想答案 |
|------|---------|---------|
| 制度查询 | "年假怎么算？" | 根据《员工手册》第5章：入职满1年享5天年假，每增加1年+1天，上限15天 |
| 流程咨询 | "出差报销需要什么材料？" | 根据《财务报销制度》：出差申请单+发票原件+行程单，3个工作日内提交 |
| 技术规范 | "后端API接口的命名规范是什么？" | 根据《代码规范》第2章：RESTful风格，驼峰命名，/api/{模块}/{操作} |
| 精确查询 | "月薪大于1万的研发部员工有哪些？" | MySQL精确过滤：张三(研发-高级工程师-15000)、李四(研发-架构师-20000) |

#### 5.1.2 答案溯源引用

**功能描述**：每个答案附带引用来源——来自哪份文档、哪个章节、相似度多少。员工可以点击来源查看原文。

**业务价值**：
- 员工信任答案（不是 AI 瞎编的）
- 合规审计："这个决策依据来自哪份文件的哪个条款"
- 知识发现："原来这个问题在《XX 制度》里有规定，我之前不知道"

#### 5.1.3 流式逐字输出

**功能描述**：答案不等待完整生成，而是逐字动态出现在屏幕上（像 ChatGPT 一样）。

**业务价值**：
- 体验更好：不用等 20 秒看一堵白屏，首字 2 秒内出现
- 感知更快：实际上完整答案可能 20 秒，但用户看到字在跳就觉得"快"
- 可打断：用户看到前几个字发现问错了，可以直接重新提问

#### 5.1.4 结构化条件查询

**功能描述**：系统能理解数值、日期等精确条件的查询，不只是模糊语义搜索。

**对比示例**：

| 查询类型 | 问题 | 传统语义搜索 | 结构化查询 |
|---------|------|------------|-----------|
| 数值范围 | "月薪大于1万的研发部员工" | 可能召回"月薪不是1万"或"行政部薪资" | MySQL B+树精确过滤 → 只有研发部+薪资>1万的 |
| 日期范围 | "2024年入职的员工" | 忽略年份，返回任意年份入职的 | `WHERE hire_date >= '2024-01-01'` 精确过滤 |
| 枚举匹配 | "哪些项目是'已完成'状态的？" | 可能混淆"进行中"和"已完成" | `WHERE status = 'COMPLETED'` 精确匹配 |

#### 5.1.5 答案反馈闭环

**功能描述**：员工对答案点赞或点踩，点踩时可选原因（答非所问/信息过时/内容不完整/引用错误）。

**业务价值**：

```
点赞 → 统计"高质量答案指标" → Dashboard 展示满意度趋势
点踩 → 记录原因分类 → 管理员查看"哪些文档的答案质量低"
     → 触发文档更新提醒 → 知识库持续改善
     → 长期数据支撑 Prompt 优化和模型微调决策
```

### 5.2 多源数据接入（扩展功能）

**解决的业务痛点**：痛点 2（数据孤岛）

#### 5.2.1 数据源统一接入

**功能描述**：不只支持手动上传文件，还能自动从企业现有系统拉取数据。

**支持的数据源类型**：

| 数据源类型 | 说明 | 典型场景 |
|-----------|------|---------|
| JDBC 数据库 | ERP/CRM 等关系型数据库 | 拉取员工表、部门表、项目表 |
| REST API | OA/门户等有 API 的系统 | 拉取审批流程、通知公告 |
| 文件系统(S3/NFS) | 共享盘/对象存储 | 自动监听新上传的 PDF/DOCX/CSV |
| 手动上传 | 现有功能保留 | 临时文件、单份制度更新 |

#### 5.2.2 增量同步

**功能描述**：不是每次都全量拉取，只同步变化的数据。

- 数据库：通过 `update_time` 字段或 CDC 日志捕获变更
- API：通过分页游标增量获取
- 文件系统：通过文件修改时间戳过滤

**业务价值**：
- 减少对源系统的性能影响（不做全表扫描）
- 知识库数据保持"准实时"（不超过 30 分钟延迟）
- 同步失败有断点续传，不丢数据

#### 5.2.3 多源数据统一标准化

**功能描述**：不同系统的数据字段名、编码规则、日期格式都不一样，进入知识库之前全部统一。

**示例**：

```
ERP 系统:   {emp_name:"张三", dept_code:"D01", salary:15000,  hire_date:"2024/01/15"}
OA 系统:    {displayName:"张三", department:"研发部", 入职日期:"2024年1月15日"}
CRM 系统:   {contact_name:"张三", org:"研发", salary:"15,000.00"}

        ↓ ETL 标准化管道 ↓

知识库统一格式:
{
    "员工姓名": "张三",
    "所属部门": "研发部",
    "月薪": 15000,
    "入职日期": "2024-01-15",
    "来源系统": "ERP",
    "数据域": "HR",
    "自然语言描述": "【HR-ERP系统】员工姓名为张三，所属部门为研发部，月薪为15,000元，入职日期为2024年1月15日。"
}
```

### 5.3 知识管理

**解决的业务痛点**：痛点 3（经验在脑子里，不在系统里）

#### 5.3.1 文档全生命周期管理

```
上传 → 解析 → 切片 → 向量化 → 入库 → 可检索 → 更新 → 删除
 │                │                    │
 │                │                    │
 ▼                ▼                    ▼
状态追踪        失败重试             归档(软删除
UPLOADED        DLQ 死信队列         即刻不可检索
READY/FAILED    自动3次退避重试      异步物理清理)
```

#### 5.3.2 扫描件识别

**功能描述**：自动检测 PDF 是否为扫描件，如果是则用 OCR 识别文字。普通 PDF 正常提取文字和表格。

**业务价值**：很多企业的存量文档是扫描版（比如带公章的制度文件、扫描存档的合同），如果不能识别，这些文档等于不存在于知识库中。

#### 5.3.3 表格结构化保留

**功能描述**：PDF 和 Word 中的表格，提取时保留为 Markdown 表格格式，而非打乱成无结构的文本。

**业务价值**：一份《薪资等级表》如果表格结构被打乱，切片后的内容是乱的——"P5P6P7 15K20K25K 3年5年8年"——完全不可读。保留表格结构后 AI 能正确理解行列对应关系。

### 5.4 权限管控

**解决的业务痛点**：痛点 4（敏感数据无防护）

#### 5.4.1 五维度权限模型

| 维度 | 说明 | 示例 |
|------|------|------|
| **角色** | admin 全权限 / user 受约束 | admin 能管理数据源，user 不能 |
| **部门** | 只能访问本部门或被授权域的数据 | HR 员工看不到研发部文档 |
| **密级** | 只能访问 ≤ 自身密级的文档 | 密级 1 的员工看不到密级 3 的薪资文件 |
| **职级** | 关键操作需要特定职级 | 只有 manager+ 能上传文档 |
| **时间/环境** | 可选约束 | 工作时间外禁止访问机密文档（可选） |

#### 5.4.2 权限演进路径

```
第 1 阶段：RBAC（当前默认）
  admin / user → 粗粒度，快速上线

第 2 阶段：+ 部门属性
  HR / 财务 / 研发 隔离 → 基础数据安全

第 3 阶段：ABAC 全维度（目标）
  五维度属性组合 → 符合等保 2.0 / GDPR
```

#### 5.4.3 审计日志

**记录内容**：谁、在什么时间、从哪个 IP、尝试什么操作、访问了什么资源、结果如何（允许/拒绝+原因）。

**业务价值**：等保合规要求的"访问审计"、安全事故溯源、权限策略评估。

  → 张经理 30 秒了解到他想知道的信息

价值:

## 7. 数据安全与合规

### 7.1 数据不出企业

| 层面 | 策略 |
|------|------|
| **部署** | 全部部署在企业内网，MySQL/ChromaDB/LLM(Ollama) 均本地运行 |
| **LLM** | 默认使用本地 Ollama (qwen3:4b)，数据不经过外部 API |
| **备用链路** | DeepSeek API 仅用于 Ollama 故障时的降级，且仅传输脱敏后的检索上下文 |
| **外部依赖** | 无强制外部依赖，可完全离线运行 |

### 7.2 访问控制

见 [4.4 权限模型架构图](#44-权限模型架构图) 和 [5.4 权限管控](#54-权限管控)。

### 7.3 安全机制清单

| 机制 | 说明 |
|------|------|
| BCrypt 密码加密 | 自适应哈希，自动加盐，强度 2^12 轮迭代 |
| JWT 双令牌 | Access Token (30min) + Refresh Token (7day)，支持静默刷新和强制登出 |
| 数据源凭据加密 | Jasypt 加密存储，密钥通过环境变量注入 |
| SQL 注入防护 | MyBatis-Plus 参数化查询 |
| 文件上传校验 | 类型白名单 + 大小限制 + 文件名过滤 |
| 全链路审计 | TraceId 串联请求，权限拒绝全量记录 |
| 传输安全 | 支持 HTTPS，内网建议也启用 |

## 10. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| LLM 回答不准确 | 员工不信任系统，弃用 | 中 | 答案溯源引用 + 反馈闭环 + 持续优化 Prompt |
| 文档量增长后检索变慢 | 用户体验下降 | 中 | 混合检索 + 域路由裁剪 + 缓存 + ES 扩展 |
| 跨部门推动阻力 | 数据源接入困难 | 高 | 先做手动上传跑通 MVP，再逐个对接系统 |
| Ollama 服务不稳定 | 问答中断 | 低 | 自动熔断降级 DeepSeek API |
| 敏感数据泄露 | 安全事故 | 低 | ABAC + 审计 + 数据不出企业 |
| 员工不愿用（习惯难改） | 系统空置 | 中 | 在 OA/钉钉内嵌入口 + 新员工培训加入 + 建立"知识贡献"激励 |
